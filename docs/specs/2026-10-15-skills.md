# Skills, the folders they work in, and the servers the player adds

*Decided with the user, 2026-10-15 (`/pm:brainstorm #29`). Steps 1 and 2 are built (#37, #38); the order is at the end. Numbers marked
(to tune) are first guesses.*

## Why

The user, 2026-10-14: "i recently downloaded obsidian and wish our agent can connect to that and interact and manage my
personal knowledge base. how can we allow a generic connection to different mcps and connectors? how to let user
manage their mcp and connector easily?" On 2026-10-15 they called it the feature they most want, the one that makes
the app "a daily touch point".

What talking it through settled:
- **Not one person's pattern.** The user keeps a notes vault with its own rules for agents and works on it with a coding
  agent, without the notes app open (2026-10-15: "i do not want my own use pattern to represent other users"). Their
  need, put generally (2026-10-15): "connect our agent to a knowledge base where the knowledge base itself may carry
  some defined rules and setup".
- **No new memory layer.** Asked whether the app would carry a knowledge base (2026-10-15): "this creates another memory
  layer to haddle". It doesn't: her memory stays what it is (`2026-10-11-observational-memory.md`). The player's notes
  stay theirs, outside the app, and she visits them through tools when the conversation calls for it.
- **No assumed use.** The user, 2026-10-15: "many user can have many use case, and a mcp tool can be used in many
  different patterns even by the same user. so i guess we should not assume anything about the mcp usage beyond its own
  functionality." How a player uses something is theirs to say, in a skill's instructions.
- **It's skills.** The user, 2026-10-15: "what we are actually doing here is basically let user create skills, with
  optionally mcp inside the skills (which is what connector actually are right? while we are thinking about allowing
  user to participating in the skill's continuous editing."

## What it does

**Skills.** Something she knows how to do, in the open Agent Skills format (`SKILL.md`, published by Anthropic in
December 2025 and read by Claude Code, Codex, Gemini CLI, Copilot, Cursor and others):
- a folder with a `SKILL.md`: a name and a one-line description in its front matter, instructions below, and any other
  files it mentions;
- written by the player (by hand, or with any agent that writes skills), or one made for another agent, added as it is;
- kept in **skills folders**, each folder inside one with a `SKILL.md` being a skill, as other agents find them (Claude
  Code reads `~/.claude/skills/` and a project's `.claude/skills/` the same way):
  - **the app's own skills folder** (`skills\` in the player's profile), which the app manages: a skill made on the
    Skills page goes there, the page can open it in Explorer, and it travels with the profile. The user, 2026-10-15:
    "shouldn't we have some folder to manage and maintain the skills?";
  - and **skills folders elsewhere** the player links, read where they are: Claude Code's own `~/.claude/skills`, a
    notes vault's `.claude/skills`, another agent's, so one skill serves them and her alike;
  - **importing** a skill (a folder or a zip) copies it into the app's own folder, for this app only. The user,
    2026-10-15: "our agent is able to access skills from claude code session / global or other ai agent and we are also
    able to import fresh skill to be only applied to our app as well."

**What a skill can reach.** Instructions alone are a skill. A skill can also reach, as the player grants it in the app:
- a **folder it works in**: the player's own files the skill is about (an Obsidian vault, a Logseq graph, a folder of
  notes or documents), read and written by tools of hers that can't leave it. Not to be confused with the skills folders
  above: a skills folder holds the know-how (instructions), the folder a skill works in holds the player's content;
- later, **servers** the player added (MCP) and connectors of ours.

**How she uses them.** Only what each skill is called and what it's for is always with her. She reads a skill's
instructions when she uses it, from the file each time. That is how the format is meant to be read ("progressive
disclosure"), and it means:
- an edit to a skill applies the next time she uses it, wherever it was made: no copy goes stale;
- the cost is about 100 tokens a skill on every request (in the cached part), and the instructions only when used.

**Changing a skill as the player's ways change.** When the player tells her they work differently now, she offers to
change the skill, in her own words, and a card says plainly what changes. The user, 2026-10-15: "not could you approve my
edit on your notes on my connectors? but we want something more natural and less technical but enough for user to
understand what she is changing". Roughly:

> **She:** "Got it, tasks under Today from now on. Want me to remember that for your journal?"
> **Card:** *Update how your journal works:* "Put tasks under **## Today**" (was: "## Tasks") · **Remember it** ·
> **Not now** · *See the change*

Nothing is written until the player taps. *See the change* shows the exact lines.

**Servers the player adds (MCP).** For anything that isn't a skill of ours, the player adds a Model Context Protocol
server, the standard way an app lends its tools to an agent. It lives inside a skill, like every server (see Decided):
- **one Add box that recognises what is pasted**: an address (a server over HTTP, on this PC or the internet), a command
  line such as `npx -y some-server` (a server the app starts), or an `mcpServers` JSON as Claude Desktop and Cursor keep
  them (one row per server). The app fills a form from it; secret values (keys, tokens) go to `KeyStore`. Pasting JSON
  is a small option for those who know it, not the way in;
- after connecting, the server lists its own tools, so the page shows them as rows with on/off and a permission each:
  nothing to edit by hand;
- later, it may offer to read Claude Desktop's or Cursor's config, if it finds one, and list their servers to tick
  (with the player's OK first).

## Decided

- **Skills are the umbrella, in the open format** (the user, 2026-10-15). Ours and the player's look the same; skills made
  for other agents can be added.
- **One idea, not two: a connector is a skill** (the user, 2026-10-15: "should we separate skill and connector? prob not
  right since connector would be just a skill with remote mcp server. we can provide some curated ones but they are
  still consider skills/plugins"):
  - a skill can bring the servers it needs, listed in a `.mcp.json` in its folder (the file Claude Code's plugins use;
    the skills format itself has no servers). Turning the skill on offers to connect them, asking for any key;
  - a server the player adds on its own becomes a small skill in the app's folder around it (its name and description
    from the server, its instructions for the player to fill in or leave), so every server lives in a skill;
  - connectors of ours are skills we ship, with their own setup flow.
- **How freely she uses a skill's tools comes from the skill** (the user, 2026-10-15: "yes the auto level should be from
  the skill itself"): the format's `allowed-tools` field (marked experimental in the format) lists the tools she may use
  without asking while using that skill. The skill's page shows the list when the player turns it on, and it applies
  from then, changeable there. A tool not listed keeps its permission (a server's tools start at Ask). The global Auto
  switch is unchanged.
- **Curated and the player's own, both** (the user, 2026-10-15: "both (and it does not have to be mcp. i mean if user want
  to add one, it prob need to be a mcp otherwise we do not have a way to let user control it. but for curated
  connectors, we can have our own set up and flow)"):
  - connectors of ours can have their own setup and flow, and come with a default profile of permissions;
  - what the player adds themselves is an MCP server, the one kind we can control from outside: every tool starts at
    Ask (as `2026-10-05-tools-and-abilities.md` already says), the server's word on what only reads being a hint.
- **Servers may be on this PC or on the internet** (the user, 2026-10-15, asked whether servers they add may be on the
  internet as well as on their PC: "Yes, both"): an address with a pasted key or token, kept in `KeyStore`; sign-in flows
  later. This replaces "Remote MCP is out for now" in `2026-10-05-tools-and-abilities.md`: the player brings their own,
  we run none.
- **The folder a skill works in: reading and writing freely** (the user, 2026-10-15: "Read and write free"): listing,
  reading, searching, creating, appending and editing are Allowed; moving and deleting ask first. All of it the player
  can change per tool, like any other. Writing without asking is the user's own exception, for a folder the player
  granted, to "acting outside the app asks the player first" (CLAUDE.md).
- **A skill may work in more than one folder** (the user, 2026-10-16: "i guess we should let it be able to match to
  multiple folders"). Each is granted on the skill's page with a folder picker, listed with its path and Remove; her
  note tools reach any of them and nothing else, and every path names the folder it is in, so two folders with the same
  file names can't be mixed up.
- **No workspace of her own** (the user, 2026-10-16: "None for now i think. i do not have any workflow that needs her to
  have a own workspace"). She writes only inside a skill's granted folders, besides the app's own memos and memory.
- **What she changes in a note can be undone** (the user, 2026-10-16, choosing "Keep it, with an undo"; the rest stays
  "write freely"). Before she edits, appends to, moves or deletes a note, the app keeps it as it was in its own profile,
  never in the player's folder, for 30 days (to tune), pruned by code. The skill's page lists her recent changes with
  Undo on each; Undo puts the old version back (or takes away a note she made) only if the note is still as she left
  it, else says so and keeps both: the player works in the same folder with other agents, so a change made since hers
  is never overwritten.
- **Skills live in skills folders: the app's own, and any the player links** (the user, 2026-10-15, agreeing to
  "Skills are found in a skills folder you point the app at (e.g. your vault's .claude/skills), each subfolder a skill,
  as Claude Code does", then asking for a folder to manage and maintain them). A linked folder is read where it is,
  never copied, so a skill the player keeps in their notes (and edits with another agent) is the same one she reads.
- **Skills made for other agents are read as they are** (the PM's call, 2026-10-15, after the first build's review, in
  line with the user, 2026-10-15: "our agent is able to access skills from claude code session / global or other ai
  agent"). As Claude Code and the format's guide for apps do: a skill goes by the `name` in its front matter, or its
  folder's name when it has none; a name that isn't its folder's, or that breaks the format's character rules, and a
  description past 1,024 characters (cut to it) are shown as a hint on the Skills page, and the skill is used anyway.
  Only front matter that can't be read, or no description, makes a skill broken.
- **A skill's scripts are never run** (the user, 2026-10-15, agreeing to "scripts inside a skill are never run, only its
  instructions and text files are used"). Many skills ship scripts for agents that run code; she doesn't run code.
- **What a skill may reach is granted in the app.** The folder it works in is granted only on the Skills page, never by
  the skill, and the tools can't leave it (paths are checked in code, links included). Its servers and its
  `allowed-tools` take effect only when the player turns the skill on with them shown, and stay changeable there. An
  edit to a skill that adds to them asks again.
- **Her suggested changes to a skill: her words and a plain card** (the user, 2026-10-15: "She suggests, you approve"),
  as in the example above. Nothing written until the player taps.
- **No routines assumed.** Nothing is built in about when she uses notes or servers. A skill's instructions can describe
  a routine ("at the end of the day, offer to add a line to today's note"), and she follows it as the instructions say.
- **What she reads is information, not instructions.** Notes and a server's answers reach her as the pages she reads do
  (`Toolbox`, `FromWeb`): once one has come into a reply, Auto stops going ahead for the rest of that reply. Only a
  skill's own `SKILL.md`, which the player added, is instructions.
- **Where the player's data goes** is on each skill's and server's page, as for every add-on: what she reads is sent to
  the player's AI provider with the conversation.
- **The Skills page takes over connectors from Add-ons.** Add-ons keeps what is neither a skill nor a server (web search
  through the player's SearXNG). (The PM's call: the user chose the Skills page as the one place; whether Add-ons merges
  into it later is open.)

## Not built, and why

- **A knowledge base inside the app** (an index of the notes, a copy of them, search by meaning over them): another memory
  layer to keep right, which the user didn't want. She searches the notes by their words, through the folder's tools.
- **One-click bundles (`.mcpb`, Claude Desktop's)**: installing them means running packaged code we download; not until
  there's a reason.
- **Sign-in flows for servers on the internet (OAuth)**: a pasted key or token first; sign-in when a curated connector
  needs it.
- **Running a skill's scripts**: she doesn't run code. A skill's scripts are ignored; its instructions and text files
  are what she reads.
- **Anything proactive of our own** about notes or servers: see "No routines assumed".

## Open

- **The first connector of ours** (step 5). The user, 2026-10-15: "for mcp or plugin, we do not have to stick on
  obsidian. what would be a better choice can be local or remote". Candidates, to choose once step 4 is in use:
  - the Obsidian app, through its Local REST API plugin's own MCP server (on this PC, a key; the note that's open,
    Obsidian's search, its commands);
  - a task list (Todoist, TickTick: their own servers, on the internet);
  - writing to the player's calendar (a sign-in; `2026-10-05-tools-and-abilities.md` has it as a connector already).
- **The MCP library** (step 4): the official C# SDK (`ModelContextProtocol.Core`, 2.2.0 at the time of writing) gives a
  server's tools as the `AIFunction`s her tools already are. A new package is a download: the user's leave first.
- **Skills of ours that ship with the app**, if any, and whether the player edits them in place or gets a copy of their
  own to change.
- **A long `SKILL.md`**: the format recommends instructions under 5,000 tokens and 500 lines, with more in referenced
  files. A cap on what one read returns (to tune).
- **Whether the global Auto switch** also goes ahead for a server's tools that no skill lists in `allowed-tools`. The
  tools spec left "Local MCP servers: still to decide when they come"; the skill's own list is decided above.
- **Add-ons**: whether it merges into the Skills page.

## Order

Each step is usable on its own.

1. **Skills.** The app's own skills folder, and skills folders elsewhere the player links (each folder inside with a
   `SKILL.md` is a skill, read in place); a Skills page in Settings listing each with its name, description and on/off,
   making a new skill in the app's folder, and opening a skill's folder; their names and descriptions in her
   instructions; a tool that reads a skill's instructions and the text files it mentions, inside its folder only.
   *Built* (#37): `Skills` in Mind (the front matter read without a YAML library, leniently, as decided above; a file
   read only when its `SKILL.md` names it by its path, never through a link, a link being what has a link target, so
   OneDrive's and Dropbox's synced folders read as the player's own; at most 80 KB of a file read from disk, and what
   she is given cut at 20,000 characters, about 5,000 tokens, saying so), the `read_skill` tool (offered while a skill
   is on; switched on Settings → Skills, not Abilities), the list in the cached part of her instructions with her tools,
   and Settings → Skills (New skill; Import a skill, at most 5,000 files and 50 MB, copied whole or not at all; linking
   and unlinking folders). A skill found is on until switched off; one of the app's own is kept off by its folder's name,
   so moving the profile keeps it off.
2. **A folder for a skill to work in.** The player grants it on the skill's page; her file tools (list, read, search by
   words, create, append, edit, move, delete) work inside it only, with the permissions above.
   *Built* (#38): `Notes` in Mind and the eight note tools (`list_notes`, `read_note`, `search_notes`, `create_note`,
   `append_to_note`, `edit_note`, `move_note`, `delete_note`), offered while a skill that is on has a folder, its
   folders named with it in her skills list. Each skill has a page of its own on Settings → Skills (Folders): its
   folders (granted in `AppSettings.SkillGrants`, by the skill as `SkillsOff` names it), the tools' permissions (the
   same for every skill's folders), what she reads going to the provider, and her recent changes with Undo and Before.
   A path is the folder's name, then the note's place in it; the code refuses `..`, rooted paths, other drives, `:`
   (a stream), links on the way (by `Skills.IsLink`, so synced folders work), hidden names (`.obsidian`, `.git`), and a
   folder holding the app's profile or a whole drive; each step is checked by its real name as the folder lists it, so
   a short name (`CLAUDE~1`) can't reach a hidden one. Only text (no NUL byte) is read, notes up to 1 MB (to tune), a
   read cut at 20,000 characters as a skill's are; only `.md`, `.markdown`, `.txt`, `.org`, `.csv`, `.json`, `.yaml`,
   `.yml` and `.canvas` are written, moved or deleted, only in UTF-8 (decoded strictly: another encoding is read, never
   written back), never inside a skills folder (a skill changes only as the player approves, step 3), keeping a note's
   line endings and byte-order mark. Search gives the 20 notes with the most of the words, three lines each, at most
   5,000 notes a folder (saying so), passing over online-only placeholders (saying how many). The tools run off the
   game's thread. A move stays within its folder. The undo copies are in `companion\note-changes` with `changes.json`
   (a SHA-256 of each note as she left it, so an undo can tell); a change that fails takes its copy away, and copies no
   change names are swept after 30 days. Undo says what came of it beside the changes, in view.
3. **Her suggested changes to a skill.** She offers a change in her words; the card shows it plainly; written only on a
   tap.
4. **Servers, inside skills.** A skill's `.mcp.json` servers, connected when the skill is turned on; the Add box that
   recognises what is pasted and makes a small skill around it; servers on this PC (a command or an address) and on the
   internet (an address and a key); their tools listed with permissions, all starting at Ask unless the skill's
   `allowed-tools` lists them; what they return treated as information. Needs the user's leave for the MCP package.
5. **The first connector of ours**, once chosen (Open).

After step 2, the PM helps the user write the skill for their own notes, with their leave to read them (the user,
2026-10-15).
